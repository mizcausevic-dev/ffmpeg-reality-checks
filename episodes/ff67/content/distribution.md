### Description

-tune zerolatency is meant for low latency streaming. What does it cost in bytes at the same CRF? We build one synthetic clip with ffmpeg lavfi (testsrc2, 320 by 240, 25 fps, 100 frames) in two versions, clean and with temporal noise (noise=alls=12:allf=t+u:all_seed=1), and encode with libx264, preset medium, one thread, a hard -frames:v 100 and -t 10 on every command.

The clip: a flat patch of the red bar is 81 in all 432 cells of every clean frame; in the noisy clip it takes 12 values from 75 to 86 and 398 of 432 cells change between frame 50 and 51. Mean luma change per frame is 2.81 clean and 6.40 noisy.

The finding, on the noisy clip at CRF 23: no tune 179174 bytes, zerolatency 428245 bytes, 2.39 times. Film is 211127 (1.18 times), animation 179591 (1.00 times). Readers: the file size and the sum of the ffprobe packet sizes give the same ratio within 3 percent. A repeat encode gives the same file.

B frames: the default has 1 I, 25 P and 74 B frames; zerolatency has 1 I and 99 P (ffprobe frame types and the x264 statistics line agree on every encode). But B frames are not most of the cost: -bf 0 alone is 197671 bytes (1.10 times). -x264-params mbtree=0 alone is 389555 bytes (2.17 times) with the 74 B frames kept; rc-lookahead=0 gives the identical bytes, and the x264 options line shows both set mbtree to 0. Zerolatency with -bf 3 put back is also 389555. The 38690 bytes between that and 428245 are the B frames. The x264 options line shows the default running bframes 3, rc_lookahead 40 and mbtree 1, and zerolatency running bframes 0 and mbtree 0.

Quality is not lower: y PSNR at CRF 23 is 36.15 dB without a tune and 36.45 dB with zerolatency (the ffmpeg psnr filter and a Node reader agree to 0.001 dB on every encode). At equal quality it still costs: the default at CRF 22 is 244638 bytes at 36.42 dB, against 428245 bytes at 36.45 dB for zerolatency at CRF 23, which is 1.75 times. Interpolating the default curve gives 1.68 times.

The cost depends on CRF (zerolatency over no tune at the same CRF): 1.27 at CRF 18, 1.59 at 20, 2.39 at 23, 1.33 at 26, 1.27 at 28, 1.09 at 30, 1.03 at 32. The default curve falls steeply between CRF 20 (760484 bytes) and 22 (244638), and CRF 23 sits just past that; I did not test why. With two threads, CRF 23 gave 418892 over 178964 bytes: 2.34 times. With two threads the same command on a loaded machine gave 140663 bytes in some runs and 141201 in others, so the fixture uses one thread.

On the clean clip at CRF 23: 141353 bytes without a tune and 197221 with zerolatency, 1.40 times, but at 46.32 dB against 42.59 dB (3.73 dB higher), so that is not a like for like cost.

The 15 tests pass on ffmpeg 6.1.1 and 8.1.2. Exact byte counts are asserted on 6.1.1 only; on other builds the tests assert relations, which also pass on 8.1.2.

Limits: one synthetic 320 by 240 clip, 100 frames, libx264 preset medium, one thread, ffmpeg 6.1.1. The noisy clip is a hard case for the encoder, so 2.39 times is what this clip gives, not a rule for every video. The step in the default curve near CRF 22 makes CRF 23 the worst point tested. Not tested: other presets, real footage, other x264 or ffmpeg builds, x265, the latency actually saved, players.
