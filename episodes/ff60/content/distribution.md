# FF60 distribution kit: FFmpeg subtitles Filter Path Escaping: 3 of 12 Open the Wrong File

All numbers below come from the synthetic fixture in `episodes/ff60/fixture/` (experiment.mjs, run.mjs) and its tests, measured on ffmpeg 6.1.1 on Linux. The tests need file names with a colon and a backslash, which Windows cannot hold, so they are skipped on the Windows 8.1.2 build: nothing here is measured on 8.1.2.

### Description

You write subtitles=name.srt, and ffmpeg says it cannot open the file. Or it says nothing, and burns other subtitles. Which characters in a path break the subtitles filter, and what actually fixes them? We write twelve subtitle files, spell each path three ways, write each string six ways, and read every frame twice.

Fixture (no footage, no network): one gray lavfi frame, 480x270, and twelve small .srt files, each with its own text, so the burned pixels name the file that was opened. The twelve paths: a plain name, a space, a colon, an apostrophe, square brackets, a comma, a backslash, a semicolon, an equals sign, a space in a folder, a folder named C: (the look of a Windows drive, but a Linux folder here) and an apostrophe in a folder. Three lookalike files (ab.srt, its.srt, dirs/sub.srt) hold different text. ffmpeg is started without a shell, so only ffmpeg's own parsing sits between the string and the file.

Readers: (1) the decoded frame in Node, compared byte for byte with the no-subtitle frame and with the frame of the same file under a safe name; (2) ffmpeg framemd5 of the same frame, compared with the same two hashes. Each run is classed right (the intended file was burned), wrong (another file was), none (nothing was burned) or error. The two readers give the same class on all 216 runs (12 paths x 3 spellings x 6 ways to write). Controls: no subtitles burns 0 pixels, the safe-name copies burn 1124 to 1163 pixels and no two look alike.

Written as is (the same for the name, ./name and the full path): 3 paths work (plain, space, space in a folder), 6 stop with an error (colon, brackets, comma, semicolon, equals sign, C:/), 3 open the wrong file with exit status 0 and no message (apostrophe, backslash, apostrophe in a folder). The frame is byte for byte the lookalike's frame. Take the lookalike files away and the same strings stop with Unable to open its.srt, ab.srt or dirs/sub.srt.

Why: the string is read twice, as a filter graph (a comma or semicolon ends the arguments: No such filter: 'b.srt'; brackets: Trailing garbage after a filter) and then as options (a colon starts the next option: b.srt read as an image size; an apostrophe and a backslash are eaten).

What fixes it, counting full paths read as the intended file out of 12: as is 3, one level of backslashes 3 (the same as as is in all 36 rows), quotes 6 (brackets, comma, semicolon only), two levels of backslashes 11, two levels with the equals sign escaped too 12. A relative name with a colon also needs ./ in front: two levels gives 9 of 12 as a plain relative name and 11 with ./, because ffprobe reads the text before the colon as a protocol (Protocol not found; ./ or file: in front opens the same file). The shell is a third layer: the two-level string for a colon works in single quotes, and fails bare or in double quotes.

The 18 tests pass on ffmpeg 6.1.1 with libass 0.17.1.

Limits: ffmpeg 6.1.1 with libass 0.17.1 on Linux, srt files, a gray test frame, ffmpeg started without a shell (plus one set of sh runs). The wording of the errors, the quoting results and the relative-colon behavior are the parts most likely to differ between builds. Not tested: Windows paths and cmd.exe or PowerShell quoting (a folder named C: on Linux is only the same text), other ffmpeg builds, other libass versions, non-ASCII names, ass files, the fontsdir option.
