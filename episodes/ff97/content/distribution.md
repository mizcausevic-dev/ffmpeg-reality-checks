# FF97 distribution kit: FFmpeg WAV Through a Pipe Carries Placeholder Sizes, so Players Guess the Length

All numbers below come from the synthetic fixture in `episodes/ff97/fixture/` (experiment.mjs, run.mjs) and its tests, measured on ffmpeg 6.1.1; also run on 8.1.2 with the same results (the fixture output matches the 6.1.1 output; the tests pass in 3 of 3 runs).

### Description

You run ffmpeg with -f wav - and capture stdout in Node, or send it to a socket, or save it to disk. Is that the same file as writing to disk? The sound is identical. The header is not. We measured both.

Input: a 440 Hz sine, 48000 Hz, stereo, 16 bit, 1 s: 192000 bytes of audio, byte rate 192000. Cases: -f wav to a file, -f wav to a pipe captured by Node, the same with -write_bext 1, with -rf64 always (pipe and file), with -f w64 (pipe and file), raw s16le plus a 44 byte header written by Node, and the pipe capture with its size fields patched.

Readers: ffprobe (format and stream duration, on the saved capture and on stdin) and ffmpeg decoding (bytes out, from a file and from stdin); and a bytes reader in Node (chunk list, RIFF size field, data size field, ds64 fields, and the duration a size trusting player computes: claimed data bytes over byte rate).

Header: 78 bytes, with the RIFF size at byte 4 and the data size at byte 74. Written to a file the fields are 0x2ee46 (192070, the file size minus 8) and 0x2ee00 (192000). Through a pipe ffmpeg cannot seek back and both stay 0xffffffff. Only those 8 of 192078 bytes differ from the file; the audio is byte for byte the same.

Players: a size trusting player gets 1 s from the file and 22369.6 s (6.2 hours) from the pipe capture. ffprobe on the saved pipe capture still says 1.0 s because it falls back to the file size: append one more second of bytes and it says 2.0 s, where a true header stays at 1.0 s. ffmpeg decodes all 192000 bytes from the file and from stdin. ffprobe reading stdin prints N/A for the duration of every plain wav, even a correct one.

Flags: -write_bext 1 adds a bext chunk (610 bytes) and the sizes stay 0xffffffff. -rf64 always on a pipe writes a ds64 chunk of zeros (riff 0, data 0, samples 0) and ffmpeg then decodes 0 bytes: worse than the plain pipe; to a file the ds64 chunk holds 192106, 192000 and 48000 and decodes fully. -f w64 on a pipe writes a data size of 0x7fffffffffffffff and ffprobe refuses the capture (Invalid data found when processing input); patching the two 64 bit fields makes it readable.

Fixes: patch the RIFF size and the data size in Node after the last byte arrives (the result equals the ffmpeg file, 192078 of 192078 bytes); or pipe raw s16le and write the 44 byte header yourself when the length is known in advance (sizes 0x2ee24 and 0x2ee00); or let ffmpeg write a file.

The 13 tests pass on ffmpeg 6.1.1.
