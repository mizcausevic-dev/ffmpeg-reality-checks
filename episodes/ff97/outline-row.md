| 97 | WAV through a pipe: what do the RIFF size and the data size say when `ffmpeg -f wav -` cannot seek back, and what do players and tools make of it? | A 440 Hz sine, 48000 Hz, stereo, 16 bit, 1 s (192000 bytes of audio), written to a file and to a pipe captured by Node. Readers: `ffprobe` and `ffmpeg` decoding (from the saved capture and from stdin), and a bytes reader in Node (chunk list, RIFF size, data size, ds64, and the duration a size trusting player computes). The header is 78 bytes; to a file the RIFF size is 0x2ee46 and the data size 0x2ee00, through a pipe both are 0xffffffff, and only those 8 of 192078 bytes differ (the audio is identical). A size trusting player gets 1 s from the file and 22369.6 s (6.2 hours) from the pipe; `ffprobe` on the saved capture says 1.0 s from the file size (2.0 s with one more second appended, a true header stays 1.0), on stdin N/A for every plain wav; `ffmpeg` decodes all 192000 bytes. `-write_bext 1` adds a 610 byte bext chunk, sizes stay 0xffffffff; `-rf64 always` into a pipe writes a ds64 chunk of zeros and `ffmpeg` decodes 0 bytes (to a file ds64 is 192106, 192000, 48000 and decodes fully); `-f w64` into a pipe writes a data size of 0x7fffffffffffffff and `ffprobe` refuses it.
