# FF59 distribution kit: FFmpeg select Keyframes: 99 Files, 4 Different, Fixed by -fps_mode vfr

All numbers below come from the synthetic fixture in `episodes/ff59/fixture/` (experiment.mjs, run.mjs) and its tests, measured on ffmpeg 6.1.1 and 8.1.2. The tests pass on both; one result differs: the default mp4 holds 99 frames on 6.1.1 and 4 frames on 8.1.2. The image files repeat the same way on both.

### Description

You select the keyframes of a clip with select=eq(pict_type\,I), expect four files, and get ninety nine. Is select broken? We run it on a synthetic clip, change only the frame rate mode of the output, and hash every file written.

Clips (lavfi, lossless x264, mkv, 96x72, 25 fps, yuv420p, no B-frames): 100 frames where frame N is a flat card of luma 16 + 2 N, so a file names its own source frame. Clip A has I-frames at frames 0, 25, 50, 75; clip B has them at 0, 10, 40, 41.

Readers: every PNG written is hashed in Node (sha256 of the bytes) and looked up in the PNGs of all 100 source frames (for the two mp4 cases, the decoded frames are hashed); ffmpeg framemd5 of the same filter chain and options; and ffmpeg's own dup= and drop= counters. They name the same source frame for every file of all 13 cases. Control: no select writes 100 files, 100 different frames, dup=0.

Default output (clip A): 99 files, 4 different frames, 95 duplicates, the files are runs of frame 0 x24, frame 25 x25, frame 50 x25, frame 75 x25, and ffmpeg reports dup=95 drop=0. Select did its job: no non-keyframe is written, all 4 keyframes appear in order. The duplicates come after it.

What fixes it: -fps_mode vfr, -fps_mode passthrough, the deprecated -vsync 0 and -vsync vfr, and resetting the timestamps with setpts=N/25/TB each write 4 files and 0 duplicates, the same 4 frames. What does not: an explicit -fps_mode cfr (99 files) and -skip_frame nokey on the input without select (99 files, 95 duplicates).

Why: an image sequence is written at a constant frame rate, and select leaves holes in the timeline, which are filled by repeating the previous frame. Clip B (keyframes 0, 10, 40, 41) gives 50 files in runs of 9, 30, 2 and 9, and the output ends after the last repeat, at output frame 49, not at the end of the clip (100 frames); with -fps_mode vfr it writes 4.

In a video on 6.1.1 it is the same: out.mp4 at the default holds 99 frames and lasts 3.96 s (on 8.1.2 the default mp4 already holds 4 frames); with -fps_mode vfr it holds 4 frames and lasts 3.04 s (3 s plus one frame).

The 11 tests pass on ffmpeg 6.1.1 and 8.1.2 (the mp4 default differs, see above).
