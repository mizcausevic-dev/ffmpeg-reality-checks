# FF77 distribution kit: FFmpeg Fragmented MP4: Header Duration 0, ffprobe Says 3 of 10 s on a Pipe, sseof Lands on the Wrong Frame

All numbers below come from the synthetic fixture in `episodes/ff77/fixture/` (experiment.mjs, run.mjs) and its tests, measured on ffmpeg 6.1.1; the tests also pass on 8.1.2 (Windows full build). Exact numbers are asserted on 6.1.1 only where the film says so; on other builds the tests assert relations.

### Description

You wrote a fragmented MP4 with -movflags frag_keyframe+empty_moov and a player says the duration is missing. Is the file broken, and can you still seek? We write a counter clip, read the file with a box reader of our own, and ask ffprobe and ffmpeg the same questions from disk and from a pipe.

Bench (lavfi, no real footage): 100 frames, 64x48, 10 fps (10 s), one keyframe every 10 frames, encoded lossless with libx264, every frame a flat card whose luma names it (16 plus 2 times the frame number), so a decoded frame reports its own id and a seek reports where it landed. Eight files from the same clip: no movflags, frag_keyframe+empty_moov, plus default_base_moof, empty_moov with frag_duration 2 s, frag_keyframe without empty_moov, dash, global_sidx, global_sidx with default_base_moof.

Readers: the first is a box reader written in Node: it walks ftyp, moov, moof, mdat, sidx and mfra, reads mvhd, mdhd, mehd, stts, sidx, tfhd and trun, and its own duration is the sum of every sample duration, not any header total. The second is ffprobe and ffmpeg: format and stream duration, nb_frames, frames decoded, and the frame a seek lands on, from a file on disk and from stdin (a pipe). Control: the regular file (ftyp, free, mdat, moov, header 10000 ms), a mehd box injected by hand, a file cut at 55 percent, and a -c copy remux.

Inside the file: the regular file has mvhd duration 10000 (timescale 1000). The fragmented file is ftyp, moov, ten moof and mdat pairs, and an mfra with 10 entries; mvhd duration is 0, no mehd, no sidx. No movflags of this build writes a mehd.

Three durations: ffprobe on a file on disk says 10.0 s (and nb_frames is N/A). The same file read from a pipe says 3.0 s (4.0 s with 2 s fragments, 1.0 s without empty_moov). The box reader adds every sample: 10.0 s. A mehd of 10000 ms added by hand, with or without a matching mvhd, changes nothing on a pipe.

Seeking: on disk every layout lands correctly: -ss 0, 3.5 and 9.9 give frames 0, 35 and 99, -sseof -2 gives frame 80. From a pipe -ss still lands right, but -sseof -2 counts back from the probed duration: frame 10 (frag), 20 (2 s fragments), 0 (no empty_moov), with no error or warning. A regular file read from a pipe lands on 80.

The index: global_sidx with default_base_moof writes one sidx with 10 references of 1.0 s (timescale 10240); a pipe then reads 10.0 s and -sseof -2 lands on 80. A sidx per fragment (dash) does not help (3.0 s). global_sidx without default_base_moof writes absolute base offsets that are 160 bytes stale (783 where the moof is at 943, the size of the inserted sidx): the file decodes 0 frames. Written to a pipe, global_sidx is dropped.

Why fragment: cut at 55 percent, the fragmented file keeps 5 whole fragments and decodes 50 frames; the regular file has lost its moov (moov atom not found, 0 frames). A regular mp4 cannot be written to a pipe (muxer does not support non seekable output, 0 bytes); the fragmented one writes 20397 bytes and decodes 100 frames. To keep a file: -c copy remux, header 10000, 0 moof, the same 100 frame hashes, a pipe reads 10.0 s.

The 17 tests pass on ffmpeg 6.1.1.

Limits: one 10 s clip, video only, lossless, one keyframe every 10 frames, ffmpeg 6.1.1. The pipe duration estimates (3.0, 4.0, 1.0 s), the -sseof landing frames on a pipe, the stale base offsets of global_sidx without default_base_moof, and the absence of mehd are the parts most likely to differ on another build. Not tested: other builds, audio tracks, browsers and players, HTTP range requests, real footage.
